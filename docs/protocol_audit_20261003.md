# R2R 适配与泛化评估协议审计

日期：2026-10-03。协议版本：2。修订发生在本项目首次官方 `val_unseen` 运行之前。本次修订采用标准 VLN 开发/测试角色，不重新训练 DUET 基座。

## 1. 已确认的事实

### 1.1 当前内部开发集不是基础模型未见环境

`src/vln_improve/protocol.py::select_partition` 用固定 seed 20261003 对 **R2R train** 的 scan 排序，取约 20% 房屋为 `train_dev`。结果是：

| 项目划分 | 房屋数 | 指令数 | 正确解释 |
|---|---:|---:|---|
| `train_fit` | 49 | 11,149 | 本项目适配参数的训练集 |
| `train_dev` | 12 | 2,890 | 适配模块的保留诊断/开发集；这些房屋属于基座的训练数据 |

官方预训练配置使用 `R2R_train_enc.jsonl` 与 `R2R_prevalent_aug_train_enc.jsonl`；官方微调代码构造完整 `train` 环境，没有本项目新增的 49/12 房屋划分。[预训练配置](https://github.com/cshizhe/VLN-DUET/blob/93e8b233164bc079a6db48b8a0a78d123ec8de41/pretrain_src/config/r2r_pretrain.json)、[微调代码](https://github.com/cshizhe/VLN-DUET/blob/93e8b233164bc079a6db48b8a0a78d123ec8de41/map_nav_src/r2r/main_nav.py)

按此来源，12 个房屋以及其中的训练指令不能称为 DUET 未见。官方 `val_seen` 也不是解决办法：它用于训练房屋内的验证。基础模型已经见过哪些数据，不会因新增模块冻结或重新划分而消失。

### 1.2 官方基座还使用过 val_unseen 进行检查点选择

项目使用官方 `R2R/trained_models/best_val_unseen`，下载来源和 SHA-256 见 [资产记录](../outputs/colab-t4-20261003T035623Z/results/artifacts/assets-manifest.json)：

`c1ed3ed27e1acbffec1fa81fbdd06e16498398809a7f80f349043ba74c21ba94`

官方 `main_nav.py` 初始化 `best_val['val_unseen']`，按该 split 的 SPL 保存 `best_val_unseen`；[官方运行脚本](https://github.com/cshizhe/VLN-DUET/blob/93e8b233164bc079a6db48b8a0a78d123ec8de41/map_nav_src/scripts/run_r2r.sh) 使用这个文件评测。这比仅凭文件名判断更有依据。作者逐步训练日志尚未取得，不能重建该二进制的每次选模历史，但应按公开流程的暴露范围保守报告。

所以官方 `val_unseen` 可以称为**训练梯度未使用的未见房屋验证集**，不能称为整个系统从未用于模型选择的盲测。把它再拆成两个房屋子集，也不能撤销上游的模型选择暴露。

### 1.3 已完成的真实基线

[结果文件](../outputs/study-20261003/baseline-train-dev.json) 记录了 frozen DUET、T4、batch 1、argmax、最多 15 次决策、完整 `train_dev`：

| 量 | 结果 |
|---|---:|
| 指令数 | 2,890 |
| SR | 97.820069% |
| SPL | 96.416810% |
| rollout 时间 | 407.975 秒 |
| PyTorch CUDA 峰值已分配内存 | 744,403,968 字节 |

峰值已分配内存不等于驱动/进程总显存，rollout 时间不包括全部下载、构建和初始化成本。此集合仅有 63 条失败；把它作为唯一选题门槛，会偏向维护基座已有表现，难以观察未见房屋需要的修正。高分与已见数据的来源一致，**高分本身不是代码泄漏的证据**。

## 2. 采用的主协议

沿用冻结官方基座，以相同初始化和输入比较新增方法与强对照。新模块仅在训练数据上拟合，官方验证集用于有限开发，隐藏测试集作为最终盲评候选。

| 数据角色 | 允许用途 | 不允许的解释或用途 |
|---|---|---|
| `train_fit` | 学习新增参数；拟合归一化；采集动作/到达训练标签；训练内划分调试 | 不把训练结果当泛化证据 |
| `train_dev` | 适配阶段保留诊断、早期回归检查、接口验收 | 不称为基础模型未见；不能作为未见环境选题的唯一依据 |
| 官方 `val_unseen` | 有记录的错误分析、有限变体/检查点选择、完整消融和 0/1/2 种子报告 | 不用其标签执行参数更新、拟合训练归一化或监督缓存训练；不称盲测 |
| 官方 `test_unseen` | 冻结方案与提交文件后进行隐藏标签评估 | 不根据分数改方案、选种子或反复试提交 |

官方 R2R 定义区分训练房屋内验证、未见房屋验证与未见房屋测试；测试只提供起点，目标路径隐藏。[官方任务说明](https://github.com/peteanderson80/Matterport3DSimulator/blob/master/tasks/R2R/README.md)

三种子和全部消融放在 `val_unseen`，报告每个种子及均值/标准差。冻结方法后，默认以预先指定的 seed 0 考虑一次基线、一次方法的 test 提交，不把验证最好的随机种子送去冒充代表性结果。测试时仍报告相同预计算特征、动作上限、回退路径计费和推理设置。

当前不要求用 61 个房屋重训 DUET，也不通过重新从全 R2R 预训练权重微调来声称“消除了已见数据”。如果未来必须获得基座级严格房屋隔离，需要在预训练和微调两阶段都排除保留房屋；这与当前低算力目标不匹配。

## 3. 开发评估预算与访问记录

### 3.1 保守起点

- 首轮先导最多 **12 个变体**，包含基线与计划比较的简单对照。变体指方法、目标及超参数组合；改变这些选择须分配新 ID。
- 先导默认 seed 0，每个变体最多评估 3 个预先指定的检查点。不能评估很多 epoch 后只登记赢家。
- 候选通过机制门槛后，冻结主方法与核心消融清单，再单独记录三种子确认预算。确认阶段的结果仍是验证集证据。
- 预算可根据诊断透明修订。修订须在额外评估前说明原因、新上限和已用次数；不能删去不理想运行，重新从零计数。

12 是限制随意搜索的起点，不是统计上保证不过拟合的魔法数字。原始基座已在这套验证集选择过，且领域长期使用该基准，论文必须报告这层现实限制。

### 3.2 每次访问登记什么

建议日志路径：`outputs/study-20261003/val-unseen-access-ledger.jsonl`。本次仅定义协议，**没有创建自动登记器或声称执行代码已经强制预算**。

每次运行前登记：访问 ID、日期、目的（基线/诊断/选模/消融/确认）、变体 ID、训练 seed、代码与配置 hash、基座与适配检查点 hash、完整 split 或固定子集 ID、预定指标和预期判断。

完成后追加：状态、输出路径/hash、实际指标、耗时/显存、是否用于选择、据此做出的决定。失败运行也保留；已经产生并查看的部分结果算一次访问。对同一缓存进行新的错误分型并据此选方法，也登记为新分析访问，不能因为没有再次运行 GPU 就忽略其开发作用。

官方完整验证才用于方案和检查点的正式选择。若为采集成本使用诊断子集，需事先固定按房屋/路径的选择方式并明确标为子集分析，不能用它的结果替代完整指标。

### 3.3 公平比较

所有方法使用相同基座、特征、额外采集数据、适配划分与近似调参预算。SR 为第一选择指标，SPL 用于打破平局；路径效率明显受损的候选需审查，不能仅因 SR 更高就宣告机制通过。

配对差值按房屋聚类报告不确定性，种子方差另外报告。11 个验证房屋不是 2,349 个独立环境；不能把指令数量当成环境泛化样本量。第二数据集/骨干需要记录场景重叠，不能默认它提供全新房屋的盲测。

## 4. 最终测试的实际状态

检索到的 [R2R EvalAI phase 页面](https://eval.ai/web/challenges/challenge-page/97/phases) 仍列出 Test 阶段及提交限制（每日 1 次，总计 5 次）。**这不等于本项目账户已能提交，也不证明服务已被本次验证。** 本项目尚未核验账户权限、测试数据/特征覆盖、导出格式和实际服务响应。

目前 `scripts/run_duet.py` 的 CLI 只包含 `train_fit`、`train_dev`、`val_seen`、`val_unseen`，测试导出尚未接入。因此 test 是候选计划，不是已完成能力。提交前先审查具体轨迹文件、检查点、协议、完整性和公开展示影响，再决定是否提交。不得自动消耗正式 test 配额进行格式试错；格式可先在允许的验证阶段检查。

如 test 不可用：

1. 如实把主要结果称为有限开发后的官方验证结果，并报告访问预算、强对照、三种子与迁移证据。
2. 不把已经多轮分析的 `val_unseen` 临时改名为 final/test。
3. 如果在任何官方验证访问前就确定无法使用 test，可另行预注册按房屋拆开发/保留子集；一旦已进入完整验证开发，就不能追溯声称其中一部分从未用于选择。

## 5. 另外两种协议为何未采用

### 5.1 全部 val_unseen 留到最后，仅 train_dev 开发

它能隔离本项目新增模块对官方验证结果的直接调参，但不能消除基座先前的验证选模暴露。更实际的问题是内部开发 SR 已接近 98%，诊断样本分布也偏向已记住的路线，可能错误淘汰真正帮助未见场景的方法。作为特别保守的研究设计可行，但当前不适合作为唯一研究反馈。

### 5.2 先把 11 个 val_unseen 房屋拆为开发/最终保留

若在观察任何结果前固定划分，可以隔离本项目新增选择对保留子集的影响。例如 3 个开发房屋、8 个保留房屋只是可选配置，不是本项目已执行划分。缺点是开发样本容易受少数房屋支配，保留集也很小，结果不再直接对应完整官方基准；上游基座仍曾在整个官方验证集选模。故不作为当前主方案，也不称为基座级全新盲测。

## 6. 最小立即行动与执行差距

本次已更新研究方案和 `configs/research_study.json` 的协议声明。下一步按顺序进行：

1. 固定本协议、基座来源、49/12 适配划分和先导预算；保留已有 2,890 指令结果，不重跑来重新命名。
2. 在首次官方验证运行前建立访问日志，登记完整基座 `val_unseen` 基线。
3. 在训练划分完成采集一致性、原样回放及未来信息隔离，再将未见环境诊断纳入登记后的开发访问。
4. 先验证机制，再开变体训练；新增模块和强对照都只在训练数据上拟合。
5. 方法冻结后核验测试导出与账户，审查具体提交，再考虑最终盲评。

**尚未同步的执行配置：** `configs/pipeline.json` 及现有训练说明仍以 `train_dev` 选择 best；本轮按任务范围没有改这些文件或运行代码。不能仅因研究配置已写 `val_unseen` 就声称实际训练选模已经切换。诊断采集 CLI 目前也仅支持训练内划分；将官方验证用于分析前，应明确接入只读分析路径，保持拟合数据限制。

这次调整纠正的是实验角色。它不改变已有原始结果，不证明主假设有效，也不构成新方法的涨点证据。
